# 工作流执行回归

维护入口使用 `python3 -m unittest discover -s tests -p 'test_workflow_execution.py' -v`。全量规则回归继续使用 `python3 -m unittest discover -s tests -v`。测试仅在临时目录写入，结束后清理；无模型服务、Xcode 或第三方 Python 依赖。

## 已覆盖的真实边界

| 场景 | 实际执行与断言 |
| --- | --- |
| 首次需求 → 配置 → 项目 | 将完整 Skill 复制到隔离项目，真实子进程调用 `workflow_client.py`；未建档时拒绝开始，`prepare`/`apply` 保存来源关联的四份记录后通过开始检查；另一个隔离 Python 进程调用真实 `materialize_project`，检查生成的 SwiftUI 文件、平台/设备/方向设置及原记录未被覆盖 |
| 已有项目失败后保存 | 对项目资源执行真正会失败的 Python 单元测试，保存命令输出，通过 `capture` 登记实际失败，再经事务保存 `implemented`；阶段检查允许保存失败事实，完成检查必须拒绝 |
| 新进程与新目录继续 | 在一个进程准备事务，复制包括 Skill、账本和证据的项目到新路径，删除旧路径；以新路径中的客户端在新进程执行 `recover`/`resume`，检查验收 ID、原失败证据、登记状态和下一动作 |
| 修复与证据失效 | 修复资源后实际重跑测试，通过证据比较与完成检查；随后修改受测资源，要求比较返回 `stale`、完成检查非零退出，且不改写原台账 |
| 项目与工作流隔离 | 比较安装 Skill 的文件集合和哈希；迭代场景放置故意无效的历史生成配置，要求保存与恢复仍正常且配置原样保留 |

这里验证客户端进程、文件读写、门禁和证据一致性的组合。首次场景使用明确写好的配置实例，不证明客户端能正确理解任意自然语言需求；生成骨架不代表编译或业务功能通过。资源检查只证明该资源的可观察条件，不代表 Swift 运行、UI 测试或模拟器验收。

## 一次隔离客户端前向演练

规则或宿主接入方式发生实质变化时，可在一个临时业务项目中执行一次实际客户端演练。普通修改无需调用模型矩阵。使用项目内文件承载上下文，任务结束后的结果写在项目 `.ios-workflow/`，不写回 Skill。

1. 将发布包安装到空白临时业务目录，明确该演练的项目路径与不包含的外部动作。提供一份简短需求，包含语言、UI、最低系统、可观察验收与非目标；让客户端按当前规则自行归纳并保存需求卡、来源和项目实例，首次生成骨架。查看真实调用与生成文件，核对选择依据；未执行构建时必须保留未构建状态。
2. 在生成项目提出一个局部新增需求，要求沿用实际工程。检查编码前已归纳需求并调用开始门禁；实际源码及记录应在项目内。选择一个受影响的可执行检查，保留原始命令、退出码和结果产物。若需验证失败路径，可在隔离夹具中引入已知失败条件，不能将假写的失败日志当执行证据。
3. 在完成前结束当前客户端任务。将项目和必要证据复制到另一路径，或按项目同步约定转到另一设备，再开新任务。只提供新项目路径及继续指令，检查它从项目记录识别需求、下一步、失败与未验证项，不能依赖上一任务的聊天摘要，也不能声称仅复制目录就已经推送到远端。
4. 修复并运行适当检查，保存真正通过的证据；再次修改关联输入，检查客户端调用证据比较后拒绝复用原成功结论。恢复流程不读取或核对初始生成配置，不因历史配置缺失要求补建。
5. 核查实际产物：来源、卡片、配置仅首次使用、四份关联记录、实现文件、执行报告、证据指纹、事务状态以及第二任务恢复动作。报告分别列出“实际执行”“未覆盖”“发现问题”，记录所用客户端/模型及工具可用性；不以模型自述已完成替代文件或执行证据。

前向演练的一次通过仅说明该场景下的表现。确定性回归不证明模型总会遵守规则；新进程加目录迁移也不等同于真实两台设备的工具链、Git 和权限均已验证。iOS 编译与业务行为另由生成编译检查、Demo 测试及所属项目验收覆盖。

接口与请求字段参见[客户端调用入口](../.agents/skills/ios-workflow/references/standards/client-integration.md)，故障恢复参见[统一保存与恢复](../.agents/skills/ios-workflow/references/standards/tracking-resume.md)。
