# 优化工作流 Token 消耗

## 原始需求

检查当前工作流的 Token 消耗逻辑，并实施必要优化。

## 需求分析

- 目标：减少建档、恢复和设计阶段的不必要上下文，同时保留跨会话追踪能力。
- 范围：需求持久化门槛、活动索引、恢复摘要、设计分级、完成与 Git 交付状态、模板、文档和结构测试。
- 验收标准：低风险单轮任务不强制建档；索引大小不随历史增长；恢复不默认读取全文；简单新增页面可使用 brief；未提交需求可验收完成；相关测试通过。
- 非目标：不修改业务项目，不估算模型侧不可观测的精确 Token 数，不删除既有历史档案。
- 影响：工作流入口、生命周期、技术设计、追溯门禁和运行记录升级为紧凑模型。
- 风险与回退：过度压缩可能丢失恢复上下文，因此保留范围版本、证据键和按需读取全文的回退路径。
- 完成定义：规则、模板、文档、运行记录和自动化测试一致且验证通过；Git 交付另行记录。

## 技术方案

- 设计等级：`full`，因为变更横跨入口、生命周期、索引、模板、门禁和兼容策略。
- 索引：升级为 v2，只保存 `last_requirement_id` 和单个活动需求摘要；历史由项目台账承载。
- 恢复：需求档案增加紧凑 `恢复摘要`，默认只读取 frontmatter、摘要和首个未完成步骤。
- 状态：需求 `done` 由完成定义决定，Git 交付使用独立 `delivery_status`。
- 兼容：既有 v1 需求档案保持只读，不要求批量迁移。
