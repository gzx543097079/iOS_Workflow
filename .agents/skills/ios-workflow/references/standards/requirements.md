# 需求分析与任务定义

编码前先把用户输入整理成最小需求卡。信息已足够时直接归纳，不重复询问；只有缺失信息会改变方案、数据或验收结果时才向用户确认。非阻塞信息使用明确假设继续。

需求来自整份文档或任务要求跨设备开发时，先按[需求接入](requirement-intake.md)解析来源和冲突，并按[建档与状态](tracking-start.md)在业务项目内持久化；只有符合下述免档条件的纯维护可仅使用上下文需求卡。

## 最小需求卡

- 目标：要解决的问题和用户价值。
- 范围：本次必须完成的行为、页面或接口。
- 验收标准：使用可观察、可测试的“条件—操作—结果”描述。
- 非目标：本次明确不处理的内容。
- 状态与异常：加载、空、错误、离线、权限、取消和重试等适用状态。
- 影响：UI、本地化、无障碍、数据/API、依赖、隐私、订阅、打点、迁移及兼容性。
- 风险与待确认：阻塞项、假设、外部依赖和回退方式。
- 完成定义：代码、测试、文档、配置和验收证据。

## 执行规则

1. 区分新增功能、缺陷修复和纯维护任务；新增功能按 `assets/templates/requirements/feature.md`，缺陷按 `assets/templates/requirements/bug.md`。
2. 新增功能与缺陷默认轻量建档。仅无关联需求、无此前持续追踪约定及跨设备等条件，且验收明确、单轮可完成的低风险纯维护可免档；仍须提供精简需求卡和免档理由。新增界面不能仅因代码少或单模块而免档。
3. 验收标准必须可验证，避免“体验良好”“正常工作”等模糊表述。
4. 发现范围扩大时先说明新增成本和影响，不静默扩展任务。
5. 需求卡明确后再进入技术方案、实现和测试。新增功能、缺陷、文档执行、跨设备、明确要求留档，或跨会话、跨模块、多阶段、高风险、共享追踪时，按[建档与状态](tracking-start.md)创建记录；已有档案的范围与验收变更按[验收与证据](tracking-evidence.md)处理。
6. 用户后续变更需求时同步更新范围与验收标准，不覆盖原始需求。

## 编码与交付检查

客户端调用 [requirement_gate.py](../../scripts/requirement_gate.py) 的 `assess_requirement_gate(project_root, task_kind=..., phase=..., card=..., requirement_id=..., low_risk=False, single_turn=False, acceptance_clear=False, continuity_required=False, related_requirement=False)`。

- `task_kind` 为 `feature`、`bug`、`maintenance`。`card` 包含非空 `goal` 文本、非空 `scope` 与 `acceptance` 文本数组，以及可为空的 `exclusions`、`assumptions` 数组。免档也须提供卡片。
- 判断参数来自实际任务和此前约定。先检查业务项目记录及 README 指向的旧记录；有相关追踪不能因新会话或缺少新格式文件而视为无记录。旧记录只读，必要来源复制到业务项目后衔接，不自动重开已完成需求。
- `phase=start` 在编码前核对卡片、索引、档案、台账和验收项关联；`checkpoint` 允许如实保存未完成或失败状态；`complete` 还核对终态及本需求证据。`gate_passed=false` 时先处理错误，不进入依赖步骤或宣布完成。
- 接口只读，不自动拦截编辑器或 Git；客户端必须实际调用，并核对卡片内容、分类和证据覆盖。结构通过不代替业务验收。首次生成前先在已明确的目标目录建立记录。
- 事后补录明确标注补录时间、原始意图和实际执行顺序；未执行的分析、批准或测试不得回填为当时已完成。已有测试仅在实际输入哈希及范围一致时复用。
