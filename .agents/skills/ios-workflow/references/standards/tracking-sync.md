# 跨设备交接、Git 关联与执行历史

跨设备交接、查询交付状态或执行历史时读取。记录属于 iOS 业务项目 `.ios-workflow/`，不属于 Skill 或共享工作目录；文件引用以业务项目根目录为基准。完成状态与远端同步状态分开报告。

## 只查询执行历史

查看执行过的需求或首次执行顺序时，只读取项目 `.ios-workflow/history.jsonc`，不加载全部需求正文、证据或初始生成配置。台账保留稳定需求 ID、首次执行顺序和当前状态；需要继续某项需求时才读取[执行与恢复](tracking-resume.md)。

## 跨设备与 Git 关联

1. 业务项目的代码、需求来源、账本、档案、交接和必要的精简证据必须能在同一 Git 仓库中同步；不能把整个 `.ios-workflow/` 忽略。缓存、构建产物和大型原始结果可按项目约定忽略，但 `verified` 所依赖的精简证据须能随项目恢复；日志和证据不包含凭证或个人敏感数据。
2. 切换设备前保存项目文件并更新交接记录，列出未完成项、阻塞项、下一动作、分支及已观察的基线。按用户当前 Git 授权提交、推送；无授权时保存本地记录并明确尚未同步，不把跨设备请求自动当作推送或发布授权。
3. 提交正文加入 `Requirement: <ID>` 和 `Steps: <STEP-ID,...>`；无关联需求的普通维护提交说明原因。Git 提交正文是需求与提交的权威关联，交付状态通过 Git 日志、上游和远端引用实时判断。
4. 新设备先读取远端最新引用，保护本地改动，再检出或安全更新到交接分支。按恢复入口核对选定需求的索引、台账、账本与档案元数据一致性，再核对实际提交、文件、相关证据及当前环境；发现远端不可达、交接提交缺失、未提交改动或未推送内容时报告可见边界，不能宣称已完整恢复。
5. 离线时可继续已明确且不依赖缺失资料的部分，交接中标明尚未同步内容；重新联网后先比较双方变更再协调合并。需求 ID、状态或证据发生合并冲突时逐项保留来源与实现，不能简单取“较新时间”或“更高完成状态”。无法证实的项退回待核验状态；产品决定冲突向用户确认。
6. 不得仅为写回当前提交 hash、推送结果或 tag 状态而新建或 amend 提交。交接记录中的基线是当时观察的恢复线索，不是永远有效的交付状态；如果已有用户要求的内容提交，可一并保存必要记录。
7. 推送失败、尚未提交、无远端或无法核对远端引用，都应明确为尚未确认同步。只有远端已包含相关代码、记录和必要证据，才能报告可在另一设备获取；仅在当前设备保存文件无法保证跨设备不丢进度。

交接前若有关联记录尚未保存，使用[统一保存与中断恢复接口](tracking-resume.md#统一保存与中断恢复接口)；存在待恢复事务时先明确恢复或放弃并协调当前记录，再交接。项目内恢复资料与其对应文件一起保留，本地协作锁不能替代跨设备 Git 冲突处理。

恢复开发时按[执行与恢复](tracking-resume.md)读取必要摘要；复用成功证据时按[验收与证据](tracking-evidence.md)核对本次相关范围，不因交接加载全部历史验收。
